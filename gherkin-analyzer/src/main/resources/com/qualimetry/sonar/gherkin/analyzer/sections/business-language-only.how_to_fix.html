Suggested alternatives

Describe the action or data, not the control type:

  • checkbox → the choice or preference: "opts in to ...", "agrees to ...", "enables ...", "turns on ..."
  • textbox / field / input → the data: "enters ...", "provides ...", "sets ... to ..." (e.g. "the user provides email ...")
  • dropdown / select → the selection: "chooses ...", "picks ...", "sets ... to ..." (e.g. "the user chooses country ...")
  • radio → the option chosen: "chooses ...", "selects option ..."
  • click → the action: "submits ...", "confirms ...", "opens ...", "navigates to ..."
  • link → the destination or action: "goes to ...", "opens ...", "navigates to ..."
  • submit → the outcome: "submits the form" → "submits the registration" or "confirms the order"
  • modal / popup / tab → the outcome or place: "the confirmation appears", "switches to ... section"

If the control type is essential to your domain (e.g. accessibility specs), you can turn this rule off for that project or use no-restricted-patterns to allow specific terms.

Compliant Solution

Use business language focused on actions and outcomes:

Feature: Account registration

  Scenario: Register new customer account
    Given the customer wants to create an account
    When the customer provides email "customer@example.com"
    And the customer sets password "SecurePass123"
    And the customer submits the registration
    Then the account is created successfully
    And the customer receives a welcome notification
